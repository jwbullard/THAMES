## Bugs observed (ranked by severity)

### Bug A — `parseMicroPhases` fatal error on configs containing glass phases

**Symptom in `*_stderr.log` (Hydration-sphere, Hydration-test-2):**

```
Data Exception Thrown:
    Details:
        Offending Function ChemicalSystem::parseMicroPhases
        Problem: No GEM phase data for a microstructure phase
```

**Symptom in `thames.log` immediately before termination:**

```
Microstructure phase C2AS is not Void but has no GEM pahse data?
```

(Typo `pahse` is in the code — leave alone unless we're already touching that block.)

**Correlation:** Both failing configs have glass phases in `hydration_products` — `C2AS(am)`, `CAS(am)`, `CA2S(am)`, `CAS2(am)`, `K6A2S(am)` (S37 added the `(am)` suffix to five glass phases). Hydration-test-1 does NOT list any glass phase and runs fine. The `_phase_mapping.json` correctly shows the suffix as `C2AS(am)`, but the fatal-error message references bare `C2AS`. So one of:

1. Error message strips `(am)` for display but the real name-match happens elsewhere — and that lookup silently fails on a subtle diff (e.g., trailing whitespace, encoding, case).
2. Two different code paths hold two different names for the same phase — display path uses `C2AS(am)` (correct S37 form), but the microstructure→GEMS lookup path holds bare `C2AS` (pre-S37 form).
3. Configs were generated by an older / newer UI than the one paired with the C++ binary the user is running, so the `_hydration_config.json` and the binary disagree on glass-phase names.

**Next diagnostic steps:**
- Extract the alpha build version the user ran (look for `version.txt`, embedded stamp, or manifest in the operations folder).
- Grep `backend/thames-hydration/src/thameslib/ChemicalSystem.cc` for `parseMicroPhases` and for the exact error string; confirm which name is being compared to which GEMS list.
- Try to reproduce locally on macOS by running `Hydration-sphere` inputs through Jeff's current `thames` binary. If it succeeds on Jeff's machine, the divergence is real and version-linked.

### Bug B — `cp` / `mv` shell commands unsupported on Windows

**Symptom in every hydration run's stderr (including the successful Hydration-test-1):**

```
'cp' is not recognized as an internal or external command,
operable program or batch file.
'mv' is not recognized as an internal or external command,
operable program or batch file.
```

Repeated many times per run. Some Python (or shell out from the app) is calling POSIX `cp`/`mv` unconditionally. On Windows `cmd.exe` there is no `cp`/`mv` — equivalents are `copy` and `move`, but the right fix is `shutil.copy` / `shutil.move` (or `pathlib`).

**Impact:** file operations that were supposed to happen (probably copying inputs into the operation folder, moving outputs into `Result/`) may be silently failing. Some outputs that Jeff and the user "should" both see could be present on macOS/Linux and absent on Windows. This alone could explain some of the reported reproducibility divergence.

**Violates:** CLAUDE.md MANDATORY Cross-Platform Safety Protocol.

**Next diagnostic steps:**
- `grep -rn "\bsubprocess.*['\"]cp['\"]" src/app/ && grep -rn "\bsubprocess.*['\"]mv['\"]" src/app/` — find the callers.
- Also search for `os.system` and any string with a literal `"cp "` or `"mv "`.
- Convert each site to `shutil` calls.
- Consider whether Windows was ever silently missing files in the Result folder for prior alpha testers.

### Bug C — no `exit_status.json` in any Result folder

Session 23-30 introduced `exit_status.json` written into `Result/` at hydration completion (used by the UI to detect FINAL-TIME vs IC-depletion vs kinetics-collapse etc.). None of the three hydration runs contain it — including the one that ran successfully to 13.5 d.

**Possible causes:**

1. Related to Bug B: the file is written to a temp location and then `mv`'d into `Result/` — the `mv` fails silently on Windows.
2. Alpha build predates the exit_status feature (unlikely — S23-30 was February 2026, alpha released May 2026).
3. Write path unconditionally uses forward slashes and fails on Windows cmd path handling.

Cross-check with `git log --oneline -- backend/thames-hydration/src/thameslib/ | grep -i exit_status` and the file writer's platform assumptions.

### Bug D — possible duplicate / overlapping phase entries in hydration_config

Hydration-sphere lists both `Hydrotalc-pyr` and `hydrotalcite`. Hydration-test-2 lists both. Also `MSH` appears alongside other similar entries in some configs. Might be intentional (two different GEMS pyroaurite-family end members) but looks like a UI bug that permits the user to select two aliases for the same phase — worth confirming when we look at the Materials Panel add-hydration-product flow. Low severity relative to A/B.
